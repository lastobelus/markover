# Markover brand implementation brief

## Intent

Markover should feel like a serious editorial tool with warmth, not like a generic developer dashboard. Its visual identity combines irregular human-drawn geometry with a quiet paper-and-ink interface. The brand should be most visible when introducing or orienting someone, then recede once they are working.

The implementer should use the exact vector sources and palette below. Do not redraw the mark, substitute type for the logotype, or use the earlier generated logo-study SVGs.

## Canonical assets

- `design/brand/markover-mark.svg` — standalone two-pane mark.
- `design/brand/markover-logotype.svg` — standalone custom “Markover” lettering.
- `design/brand/markover-lockup.svg` — final fixed-spacing horizontal lockup.
- `design/brand/markover-app-icon.svg` — approved 1024-square app-icon master.
- `design/brand/markover-app-icon.png` — required 1024-square Electron runtime raster.
- `favicon.svg` — root project favicon for T3Code; Pages retains its published copy under `docs/assets`.
- `design/brand/mockups/index.html` — reference compositions for each surface and UI state.

The three SVGs preserve the paths copied directly from the Affinity source. Keep them as external SVG files rather than duplicating the path data into application components.

## Interface palette

| Token | Value | Use |
| --- | --- | --- |
| `--brand-orange` | `#c94e1f` | Primary brand ink, active accents, focus indicators and selected-state emphasis |
| `--brand-burgundy` | `#6d211f` | Secondary brand ink, deep actions and high-contrast branded controls |
| `--ink` | `#26211e` | Primary text and strong neutral icons |
| `--muted` | `#756d67` | Secondary text, metadata and quiet labels |
| `--paper` | `#eee8e0` | Application or page canvas |
| `--surface` | `#fffdf9` | Cards, panes, headers and elevated working surfaces |
| `--line` | `#ddd5cc` | Dividers, borders and low-emphasis structure |
| `--brand-soft` | `#f5e3da` | Selection bands, quiet branded backgrounds and low-emphasis highlights |

Use solid colors. Avoid gradients in identity artwork, glass effects, saturated shadows or generic blue focus colors. Warm shadows may use the burgundy family at very low alpha.

The tested contrast ratios against `--surface` are 4.50:1 for orange, 10.95:1 for burgundy, 15.67:1 for ink and 4.99:1 for muted. Do not lighten the orange when it carries normal-sized text; it already sits at the WCAG AA boundary.

## Color consistency decision

The copied Affinity paths currently contain several visually indistinguishable ±1 RGB variations. Before generating palette variants, normalize every warm path to `#c94e1f` and every dark path to `#6d211f`, unless the designer confirms that the differences were deliberate.

After normalization, palette variants should be generated by replacing these two semantic inks. Geometry, spacing and viewBoxes must remain identical across warm, ocean, olive, monochrome and reversed variants.

## Brand visibility by context

Brand prominence is state-dependent:

1. **Introductory surfaces:** use the full lockup and a short descriptor. Examples: README leader, Pages landing page, social cards and the empty app workspace.
2. **Orienting surfaces:** use the complete lockup with the descriptor directly beneath it. Example: expanded documentation navigation.
3. **Working surfaces:** use mark plus a restrained logotype, or the mark alone. Examples: the desktop app while a document is open.

Do not show a tagline inside the working app. Once someone is using Markover, promotional language is unnecessary and visually gauche.

## Desktop app states

### Document open: mark plus restrained logotype

- Render the mark approximately 38–42 px wide.
- Render the logotype so the capital `M` is about 55% of the mark's rendered height.
- Vertically center both pieces as one quiet unit.
- Do not include a tagline.
- Give document identity and actions more visual priority than the brand.

### Document open: mark only

- Use the same 38–42 px mark.
- This is the preferred treatment when header space is constrained or the product should feel especially tool-like.
- The accessible name belongs on the containing link or header landmark; decorative images should use empty alt text.

### No document open

- Keep the application header minimal.
- Center the complete horizontal lockup in the empty workspace.
- Place “Structured review for Markdown” below it as live text.
- Provide one clear `Open Markdown` action.
- Remove the empty-state branding as soon as a working document is shown.

## Documentation states

### Collapsed table of contents

- Show the mark alone at approximately 32–42 px.
- Use compact navigation indicators beneath it.
- The mark acts as the persistent home/orientation affordance.

### Expanded table of contents

- Show the complete lockup at a comfortable fixed width.
- Show “Structured review for Markdown.” as live text directly beneath it, left-aligned with the mark.
- Preserve the vertical lockup's relative scale and spacing as one identity unit.
- Separate the brand block from navigation items with `--line`.
- Collapse back to the mark-only state rather than scaling the complete identity below its comfortable size.

## Public surfaces

- README: use `markover-readme-leader.svg` for the vertically stacked lockup and descriptor composition, followed by live navigation links and badges.
- GitHub Pages navigation: use mark and logotype separately, bottom-aligned at the canonical spacing and without a tagline.
- GitHub Pages hero: keep headline, supporting copy and calls to action as HTML; do not bake them into a brand image.
- GitHub Pages footer: use the horizontal tagged lockup, with the complete lockup and descriptor bottom-aligned as one unit.
- Documentation content pane: use the vertical tagged lockup, with the descriptor directly beneath and left-aligned with the mark.
- Documentation landing page: the full lockup is appropriate in a spacious masthead.
- Repository social preview: use a solid palette background with the lockup and short descriptor on a 1280×640 canvas.
- Pages Open Graph card: use the same visual language on a 1200×630 canvas.

## App icon and favicon

The app icon uses the mark on a warm off-white rounded plate. The production master places the mark at approximately 68% of the square's width and 57% of its height, with generous optical padding around the narrow gap and folded corner. The 1024 PNG is wired to Electron's window icon and macOS Dock icon.

The root `favicon.svg` uses the unmodified mark and remains legible at 32 px and 16 px in the current rendering check. Only create a micro-adjusted mark if real browser testing reveals inconsistent gap closure.

## Implementation constraints

- Preserve SVG aspect ratios; never stretch a component to fit both width and height.
- Keep logo images out of button backgrounds and selection bands.
- Do not add drop shadows to the SVG artwork itself.
- Keep descriptors as live text, not paths or pixels.
- Use the exact public descriptor “Structured review for Markdown.” including punctuation.
- Use the lockup only where its fixed spacing is advantageous; use separate mark and logotype assets in responsive headers.
- Provide a single accessible “Markover” name per brand cluster and empty alt text on adjacent decorative pieces.
- Do not introduce a compatibility layer for the old `M/` placeholder. Replace it directly when implementation begins.

## Acceptance checks

- App header can switch between mark-plus-logotype and mark-only without shifting document actions.
- Empty app state shows the complete lockup and descriptor, then disappears when a document opens.
- Documentation navigation shows mark-only when collapsed and the vertically tagged identity when expanded.
- Pages footer shows the horizontally tagged identity without substituting ordinary text for the logotype.
- The mark remains distinct at 16, 32, 42 and 128 px.
- Palette tokens match the values in this brief exactly.
- No raster logo appears in README, Pages HTML, documentation navigation or the working app header.
- Required PNGs are limited to platform icons and social cards.
