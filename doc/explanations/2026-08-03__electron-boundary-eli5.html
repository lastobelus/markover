Issue 22 · Electron shell

Three rooms, one careful doorway.

Markover's window should be pleasant to use, but it should not automatically inherit every power of the desktop app. This change writes down exactly what may cross that boundary—and asks TypeScript to check both sides.

Where this picture is true Proposed · PR 38

This is a snapshot of the architecture proposed by PR #38, written on August 3, 2026 while the PR was open. It explains that change—not a permanent, canonical map of Markover. Follow the PR and the linked roadmap for current status.

The stable center: the renderer reaches desktop powers through a narrow preload-owned capability surface. The exact methods, runtime enforcement, and responsibilities behind that doorway are expected to evolve.

The Tiny Story

Imagine the app as an office. The reading room shows Markdown. The building manager can open files, read the clipboard, and save work. A small front desk stands between them. Before this PR, the front desk had a handwritten list of services. Now it has one exact, shared menu: if either side misspells an order or changes its shape, the build fails before Markover ships.

What crosses the doorway

The reading room never receives Electron's raw messaging machinery. It receives only the named Markover actions exposed by the front desk.

What this PR changes

Shared vocabulary

One contract names every capability

Documents, screenshots, settings, review status, and callbacks now have shared shapes instead of being implied independently in several files.

Exact front desk

The preload object must satisfy the contract

Adding, removing, or mistyping a bridge method becomes a compile error. Raw ipcRenderer is still not handed to the page.

Typed manager

Electron callbacks stop being mystery values

Window state, IPC events, stored reviews, and asynchronous replies are now checked under the repository's strict TypeScript rules.

Release guardrail

Source is TypeScript; the app still ships JavaScript

The ordinary build emits the three Electron files the packaged app expects. No runtime TypeScript loader or module-system redesign was introduced.

Important boundary: types are a build-time alarm, not a runtime guard

TypeScript catches mistakes made by this codebase. Its types disappear after compilation, so this PR does not claim to validate hostile IPC payloads at runtime or create a new authorization policy. That security review is a separate decision. This PR does preserve Electron's existing contextIsolation setup and its narrow exposed capability object.

What does not happen

The main process is not split into a new architecture

The same responsibilities stay in the same Electron modules. This PR adds explicit types rather than a second refactor.

The browser fallback is not removed

window.markover remains optional because the renderer can run with its existing browser fallback when Electron is absent.

The packaged app does not interpret TypeScript

The standard compiler produces build/src/main.js, preload.js, and app-menu.js before packaging.

No extra Electron power is exposed

The renderer receives the exact bridge object. It does not receive ipcRenderer, Node's filesystem API, or an open-ended send function.

Validated on the supported release path

How we know the doorway still works

  • Strict lint, typecheck, notices, and all 172 tests pass.
  • The complete check and test suite pass on Node 22.13 and Node 24.
  • The macOS arm64 app packages and passes strict code-signature verification.
  • The packaged ASAR contains the three emitted Electron JavaScript files.
  • A focused test asserts that the preload exposes one typed object and never exposes raw ipcRenderer.
