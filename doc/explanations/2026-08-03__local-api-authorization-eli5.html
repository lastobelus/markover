A locked note beside a local door

Markover’s API still lives on your own machine. The change is that knowing the port is no longer enough: a caller must also read a short-lived secret protected by your OS account.

Where This Is TrueImplemented locally · pre-draft PR · 3 Aug 2026

This explains the first authorization-boundary PR on issue 12, implemented on agent/launch-api-capability-token. The stable center is the OS-account capability boundary. Restart recovery and stale-port impersonation belong to PR 2; exhaustive adversarial evidence and final public privacy claims belong to PR 3. Issue 39 independently owns bounded-loss crash/restart durability.

The Tiny Story

Before

Any local process that found Markover’s loopback port could call review routes.

Now

Every non-health call needs a fresh Bearer capability stored in a 0600 sibling file.

Still true

A process already running as you can read that file. This is an OS-account boundary, not same-user sandboxing.

Who gets through?

The filesystem decides who may learn the capability; the HTTP service checks it before it even decides whether a route exists.

One process lifetime

The public endpoint is written last. That makes it the “ready” sign: a client should not see new discovery metadata before its matching credential exists.

What this PR deliberately does not solve

Same-user attackers

A process running as you can read the same 0600 file. Preventing that needs a different isolation model.

Stale-port impersonation

Robust mismatch retries, recovery, and proof that the old port still belongs to Markover are PR 2.

Crash durability

Issue 39 owns the rule that a crash or restart must lose no more than a few seconds of review work.

Compatibility machinery

Protocol 2 is a clean break. Historical review JSON stays untouched; the newest app does not have to open it.

The practical checks

Automated

  • Generic 401s for missing, malformed, duplicate, and wrong credentials.
  • Authorization before route lookup, body parsing, callbacks, or mutation.
  • Fresh client reads, record matching, restrictive modes, rotation, and CLI flow.

Live, before handoff

  • smoke:auth prepare creates a clearly labelled real review and stores only a token digest.
  • After an approved restart, verify proves rotation and runs get/edit.
  • The opt-in diagnostics toggle is checked manually for strict redaction.
