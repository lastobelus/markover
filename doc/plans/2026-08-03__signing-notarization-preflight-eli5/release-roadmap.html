The Tiny Story

Think of a release as a museum exhibit. Two workshops build the Apple Silicon and Intel pieces. A curator checks their labels and fingerprints, places the full set in a locked preparation room, and asks for approval. For the first new exhibit, the Intel laptop visits that exact preparation room and tries the real visitor journey. Only then does the curator open the doors—and the exhibit cannot be quietly swapped afterward.

Immutable release attestation

What collection was published

GitHub locks the release's assets and tag, then attests the published collection. Existing historical releases remain untouched.

Rollback is a fire exit, not a time machine

  • Each release names one known-good predecessor and an exact version-pinned launch command.
  • Stop Markover and back up its entire Application Support directory first.
  • The guarantee applies only while both versions use the same review-data format.
  • Bad bytes are never replaced under the same tag; withdraw, repoint latest, and publish a new version.
Settings order matters. The protected release environment, tag ruleset, and immutable-release setting are activated only after the compatible slice-2 workflow has merged to main. This branch does not mutate them.

Separate reviewed activation

Credentials cannot flip the mode

A code change must explicitly select developer-id, add secure timestamping, notarize each app, staple tickets, and change expected Gatekeeper results.

Fail closed

No quiet downgrade

Certificate, credential, or Apple-service failure stops the release. A deliberate emergency ad-hoc build uses a separate approved prerelease workflow and never becomes latest.
