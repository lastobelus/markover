Markover durability · ELI5

Autosave without the paperwork pile

Markover already saves review work safely, but today it asks the disk to save a whole new copy for every keystroke. This change keeps the safety and removes the growing queue.

Where This Is True Proposed · Issue 39 · PR 1/3

This explains the first branch, agent/autosave-bounded-core, in the accepted three-PR plan for issue 39, part of the Focused preview launch roadmap. It describes proposed branch code as of August 5, 2026; re-check the issue and eventual pull request for current status.

Stable center: review work gets a bounded, latest-state persistence path. Known movement: PR 2 adds visible failure and quit barriers; PR 3 adds crash evidence and public documentation. Issue 43 may change renderer packaging, but not this persistence model. Issue 11 later proves packaged builds on clean Intel and Apple Silicon machines.

The Tiny Story

Imagine each review has a mailbox beside one careful filing clerk. The clerk can file one copy while the mailbox holds one newest copy. If you type more, Markover replaces the note in the mailbox instead of stacking up hundreds of obsolete notes. The clerk still files the first edit promptly and must collect the newest waiting note within two seconds when storage is healthy.

One review's path

1

You type

Markover takes a complete independent snapshot of the current review.

→
2

Latest-only mailbox

New snapshots replace the waiting one. They do not form a backlog.

→
3

Careful disk write

One writer uses the existing flushed, atomic replacement file.

Every review gets its own mailbox and writer schedule, so a busy review does not block another.

What the first PR adds

Bound

Two seconds by default

Under healthy local storage, continuous typing cannot keep accepted work outside the durable snapshot for more than the configured window.

Barrier

Save exactly now

Handoff can skip the ordinary delay and wait until the supplied snapshot has actually persisted.

Recovery

Failures keep the newest copy

A failed write retains the latest snapshot and retries with bounded exponential backoff instead of losing it.

Advanced

Machine-specific override

autosaveMaximumDelayMs may be set from 100 to 60,000 in settings.json. It deliberately has no Settings UI control and takes effect after restart.

The honest limit

“Two seconds” assumes the app is responsive and local storage is healthy. A disk that cannot accept writes cannot provide that guarantee. This PR preserves and retries the newest state and reports the failure to diagnostics; the next PR makes that suspended guarantee persistently visible in the app and prevents a quiet quit.

What does not happen here

No review migration

Historical JSON and attachments stay untouched. There is no fallback reader, dual writer, or speculative cleanup.

No pretend power-loss promise

This is app crash/restart durability, not a claim against failed hardware, operating-system failure, or sudden power loss.

No quit dialog yet

The five-second shutdown barrier and Retry Quit / Quit Anyway flow belong to PR 2.

No slow CI sleeps

Fake clocks prove the timing rules immediately. The compact killed-process proof belongs to PR 3.

This explainer was created after a one-question-at-a-time design interview for issue 39. The accepted constraints include a two-second default, advanced file-only configuration, one in-flight plus one pending snapshot per review, bounded retries, independent reviews, no migration machinery, and a total ordinary CI increase below two seconds per Node lane.
